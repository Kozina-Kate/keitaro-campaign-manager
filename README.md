# Keitaro Campaign Manager

Обёртка над Keitaro на FastAPI и SQLAlchemy с интерфейсом на HTML, CSS и JavaScript.
Создание кампаний реализовано; редактор офферов будет добавлен на следующем этапе.

## Текущее состояние: этап 2

- Настройки через переменные окружения и `.env`.
- Клиент Keitaro Admin API с таймаутами и обработкой ошибок.
- Получение доменов, групп кампаний, источников и офферов.
- База SQLite, журнал операций и миграции Alembic.
- Проверка названия: обязательный префикс `test_kozina_`.
- Автоматические проверки API-клиента, конфигурации и миграций.
- Форма создания кампании с двумя потоками и проверкой справочников.
- Проверка реальных настроек перед включением кампании.
- Сохранение результатов и защита от повторного создания по ID запроса.
- Сверка неопределённого результата с Keitaro без повторной записи в трекер.

## Установка

Нужен Python 3.11 или новее. Команды выполняются из корня проекта.

```bash
git clone https://github.com/Kozina-Kate/keitaro-campaign-manager.git
cd keitaro-campaign-manager
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.lock
python -m pip install -e . --no-deps
cp .env.example .env
```

В `.env` укажите корневой HTTPS-адрес трекера **без `/admin`** и существующий
API-ключ из профиля Keitaro → «API ключи»:

```dotenv
KEITARO_BASE_URL=https://your-tracker.example
KEITARO_API_KEY=your-api-key
KEITARO_TIMEOUT_SECONDS=20
DATABASE_URL=sqlite:///./app.db
```

`.env`, база и виртуальное окружение исключены из Git. Ключ передаётся только
сервером в заголовке `Api-Key`; в ответах приложения и браузерном коде его нет.
Не публикуйте `.env` и не вставляйте ключ в README или URL.

## Миграции и запуск

```bash
alembic upgrade head
uvicorn app.main:create_app --factory --reload --host 127.0.0.1
```

- Форма создания: <http://127.0.0.1:8000/>.
- Документация приложения: <http://127.0.0.1:8000/docs>.
- Готовность базы: `GET /health` — `200`, если таблица журнала доступна;
  `503`, если необходимо проверить БД или применить миграции.
- Справочники Keitaro: `GET /api/reference-data` — списки ID и названий.

При обновлении с первого этапа также выполните `alembic upgrade head`: миграция
`0002` добавляет ID запроса, входные данные и результат операции.

## Создание кампании

1. Откройте главную страницу и дождитесь сообщения «API подключён».
2. Введите название с префиксом `test_kozina_` и код страны, например `AU`.
3. Выберите оффер, домен, группу кампаний и источник из справочников.
4. Нажмите «Создать кампанию». Приложение создаст выключенную кампанию,
   последовательно добавит два потока, проверит настройки и включит кампанию.
5. В результате появятся ID кампании и потоков, ссылка на кампанию и её настройки.

Режим ротации — `position`. Первый обычный поток содержит фильтр `country`
в режиме `accept` и HTTP-редирект на `https://www.google.com/`. Второй обычный
поток не содержит фильтров или лендингов и направляет на выбранный оффер с долей
100%. Поэтому первый поток имеет приоритет, а второй принимает остальных.

Форма сохраняет ID запроса в текущей вкладке браузера. Повторный запрос с тем же
ID не создаёт новую кампанию. Не используйте другой ID для автоматического
повтора после таймаута: операция могла выполниться в Keitaro.

Статусы журнала: `pending` — выполнение не завершено, `succeeded` — результат
проверен, `failed` — создание не выполнено, `partial` — частичное выполнение
или неопределённый результат. При ошибке приложение показывает известные ID.
Кампания не включается до проверки двух потоков; если ошибка произошла уже
после отправки команды включения, она может быть активна.

Кнопка «Проверить статус» получает сохранённую операцию и при необходимости
повторно читает настройки из Keitaro. Если активная кампания полностью совпадает
с запросом, операция отмечается успешной. Сверка не создаёт и не меняет кампании.
Если создание завершилось до получения ID или остался неполный набор потоков,
нужно проверить кампанию вручную. Удаление и автоматическое восстановление
незавершённых кампаний пока не реализованы.

### API создания

`POST /api/campaigns` принимает JSON:

```json
{
  "request_id": "e6cbcaad-739c-4c5e-a27d-3c2ce90dd430",
  "name": "test_kozina_campaign1",
  "country_code": "AU",
  "offer_id": 1,
  "domain_id": 1,
  "group_id": 1,
  "traffic_source_id": 1
}
```

ID `1` в примере условные — используйте доступные ID из `/api/reference-data`.
Для новой операции нужен новый UUID; для повтора той же — прежний.
Статус: `GET /api/operations/{request_id}`.
Сверка с Keitaro: `POST /api/operations/{request_id}/verify`.
Повтор с другим содержимым или ещё не завершённой операцией получает `409`.
Некорректные данные получают `422`, частичная ошибка создания — `502`.

## Диагностика подключения

Проверка подключения без изменения данных (выводится только число записей):

```bash
python -m app.check_connection
```

Ошибки подключения возвращаются с кодами `502`/`504`, отсутствие ключа — `503`.
Необработанные тела ответов Keitaro и секреты не передаются клиенту.
Сервер предназначен для локального запуска; перед размещением в сети потребуется
аутентификация пользователей.

Проверить версию схемы и отсутствие расхождений с моделями:

```bash
alembic current
alembic check
```

Откат первой миграции: `alembic downgrade base`. Он удаляет таблицу журнала
вместе с записями; для рабочей базы сначала сделайте резервную копию.

## Проверки

```bash
pytest -q
ruff check .
```

Тесты не обращаются к реальному Keitaro: ответы API подменяются через HTTPX,
миграции проверяются на временной базе.

Для обновления зависимостей разработчик может использовать
`python -m pip install -e '.[dev]'`. Для повторяемой установки используйте
зафиксированные версии из `requirements.lock`.
